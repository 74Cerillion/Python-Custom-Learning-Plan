A04 - Module Boundaries, Typing & Failures
Purpose: Make change and failure local rather than contagious

By the end, answer the following questions:
    1. Who owns the state?
    2. Who is allowed to transform?
    3. What does this component promise to return?
    4. If it fails, where should that failure be handled?

PHASE 3:::::::::::::::::::::::::::::::::::::::::::::::::::::::::::
You're building a small multi-module market-data ingestion program that takes a simulated external market-data response, parses it into a typed internal representation, coordinates processing, and persists the valid observation to SQLite.

This deliberately combines A01–A03 without becoming Trader.

Input

main.py should begin with a controlled/simulated external payload. Something along these lines conceptually:

raw_market_data = """
{
    "symbol": "AAPL",
    "price": 234.56,
    "timestamp": "2026-09-21T09:31:00"
}
"""

You choose the exact representation.

Required architecture
                 raw external data
                        │
                        ▼
                  ┌──────────┐
                  │  Parser  │
                  └────┬─────┘
                       │
                typed observation
                       │
                       ▼
                ┌──────────────┐
                │ Orchestrator │
                └──────┬───────┘
                       │
                       ▼
                 ┌────────────┐
                 │ Repository │
                 └─────┬──────┘
                       │
                       ▼
                     SQLite

Parser: Accepts the simulated external representation, deserializes/validates what it owns, and produces the agreed internal representation. It knows nothing about SQLite.

Repository: Accepts the internal observation and persists/retrieves it using SQLite. It knows nothing about JSON parsing.

Orchestrator: Coordinates the operation. It tells the parser to parse and the repository to persist. This is where you reason about application-level success/failure rather than stuffing coordination into either lower-level component.

Main: Composition/entry point. Instantiate the pieces, supply the controlled input, and initiate the operation.

Required behavior

Then deliberately demonstrate one failure path.

The important part is that the log contains your correlation ID but doesn't dump sensitive input.

You can put a fake credential into the simulated external context if useful:

API_KEY=SUPER_SECRET_BLAH_BLAH

Then demonstrate that your resulting error/log output does not contain it.

Don't actually use a real credential.

Definition of Done

Your program must demonstrate:

valid controlled market data travels Parser → Orchestrator → Repository → SQLite
responsibilities are separated across modules
at least one meaningful module boundary has an explicit typed interface
one correlation ID follows the same operation across multiple modules
successful persistence can be verified
one intentional failure travels to the boundary you selected during planning
logs identify the failed operation without exposing the simulated credential
you can verbally trace who owns the state at each stage and why
