QUESTIONS:
Responsibility ----
    The parser owns the validation logic and the formatting logic, but not the unit test suite or the data itself. For the purposes
    strictly of this academic exercise, I know that it technically does own the data, but that's the case in the real world. For
    educational purposes, we're assuming that it does not own the data directly.
Input Contract ----
    It expects a dictionary containing the stock symbol for identification, it's price, and a timestamp of when the data was obtained.
    That means all incoming data to this component must be normalized to this schema to be viable
Output Contract ----
    The product of successful parsing is the production of the same data in a more human readable format (keeping it simple for scope
    purposes)
Failure Contract ----
    Rejection occurs when the symbol is not a string (in the real world, you'd use an API to verify the company is legitimate and publically
    traded), when the price is improperly formatted (for this exercise, that's symbolic of the price being illegitimate), or when the timestamp
    is illegitimate (raises questions about validity, accuracy, and recency of information, which is important for time-sensitive transactions
    and logging)
Dependency Analysis ----
    This component depends on the datetime module for proper function so that we can declare strings containing a potential date and time as
    timestamps during normalization. (Program has a dependency injection on the datetime module for data normalization and verification)
Test Matrix ----
    First test is a happy path test, making sure that when I give it good information, the validate function works properly. It will take a
        dict and return the same dict, and assert that the two are equal.
    Second test is a boundary test, verifying that changing the symbol works properly. It takes a dict and should return the exact same dict
        and assert that the two are equal.
    Third test is a failure test. I'm going to give _validate bad data and expect that it should return information that's different from what
        is being passed in. If that happens, than the assertNotEqual statement will pass.
    Fourth test is the same as the third test.
Execution Flow ----
    Pseudocode above
What the tests don't prove ----
    The test does not prove that the data coming out of the formatter is formatted correctly, which is the whole point of the program. 
    The test suite does not run error handling tests, so while I can assume graceful degradation based off the pseudocode, there's no
        way to verify.
    The test suite does not test or isolate dependencies or run Object-Oriented Checks.
